## 6. 변환 규칙 · why 초안

- level: `1` → `L1` (sqlverdict는 L1~L4 문자열만 허용, 값은 그대로)
- trap: `null` → `none`, 나머지 그대로
- ordered: `scorer.is_ordered(gold_sql)` (정답 SQL에 ORDER BY 유무)
- verified: 전부 true / empty_ok: Q20만 true / snapshot: 2026-11-21
- expected: gold_sql을 `text2sql.executor.query`로 실행(읽기 전용, `scorer.run_gold`의 1,000행 검사 통과)
- 예측: pred_sql → `guard(pred_sql, 1000)` → `executor.query`. 실행 에러는 `error: "<예외명>: <메시지>"` (이번 데이터엔 에러 0건). pred_sql은 원문(guard 전) 저장

**why 초안 문항 (사람 검증 전, golden.yaml엔 verified: true로 들어가 있음)**

- Q17 (dup_join): order_payments는 주문당 결제 행이 여러 개일 수 있음(1:N). 결제 테이블을 직접 조인하면 item 행이 결제 행 수만큼 복제돼 404,020.72 → 632,719.07로 부풂. IN 서브쿼리로 주문만 거르고 매출=delivered 주문의 SUM(price)
- Q18 (unique_id): customer_id는 주문마다 새로 발급됨. 사람 단위는 customer_unique_id. 2018년 COUNT(DISTINCT customer_unique_id)=52,749 vs customer_id=54,011
- Q19 (biz_term): 사내 정의 매출 = order_status='delivered' 주문의 SUM(order_items.price), 배송비 제외. 필터 없이 price만 6,155,806.98, price+freight 7,142,672.43, 정답 5,962,902.01
- Q20 (empty_ok): 주문 데이터는 2016-09-04 ~ 2018-10-17. 2019년 주문은 없으므로 빈 결과가 정답

trap=none 16문항은 why를 쓰지 않음 (sqlverdict 규칙상 필수 아님).

## 7. sqlverdict 버그·개선점

수정은 [sqlverdict](https://github.com/songwookun/sqlverdict)에서 진행.

**0.1.0 재채점에서 찾고 0.1.1에서 고쳐진 것**

- 이름 매칭 + 위치 대체가 섞이면 남는 컬럼이 있어도 `missing_columns`로 silent_wrong → 남은 컬럼 순서대로 매칭
- 1행 결과면 항상 "값이 정확히 N배" + 조인·필터 원인 단정 → 단순 배수만 단정, 나머지는 "약 N배" (이번 Q16·Q17·Q19)
- empty_ok 문항에서 양쪽 0행인데 컬럼이 더 많으면 extra_columns → correct + 컬럼 힌트 (이번 Q20)
- correct_approx가 --baseline에서 regression → 통과로 취급, accuracy_with_approx 추가 (이번 Q03·Q09)

**0.1.1에 남은 것 (이번 데이터엔 영향 없음)**

- 버그: `compare_columns` 사용 시 비교 안 하는 정답 컬럼과 이름이 같은 예측 컬럼이 남은 컬럼 후보로 잡혀 오매칭
- 확인 필요: empty_ok 빈 결과면 정답 컬럼이 하나도 없어도 correct (missing 정보가 안 남음)
